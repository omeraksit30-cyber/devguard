# Implementation decisions

Decisions taken where the specification was silent or ambiguous. The simplest, safest interpretation was chosen.

| # | Topic | Decision |
|---|-------|----------|
| D1 | Python version | Developed and tested on Python 3.12 (Homebrew `python@3.12`); macOS system Python 3.9 is too old for `tomllib`. |
| D2 | Extra security headers | In addition to the required headers, responses carry `X-Frame-Options: DENY`, `frame-ancestors 'none'`, COOP/CORP `same-origin`, and `Cache-Control: no-store` on `/api/*`. |
| D3 | JSON content type on state-changing requests | Requests to `/api/*` using POST/PUT/PATCH/DELETE without `Content-Type: application/json` get `403 json_required`, including bodiless ones such as DELETE. The UI always sends the header. |
| D4 | Validation errors | `422 validation_error` lists only the offending field locations; submitted values are never echoed back (a body could contain a secret). |
| D5 | Fingerprint stability | A secret's fingerprint includes its start line, and a dependency's includes its installed version. If a secret moves to another line or a package version changes, the finding shows up as "resolved + new". |
| D6 | Non-npm results | `trivy fs` may report other ecosystems if their lockfiles exist. Results whose `Type` is present and not `npm` are ignored, since only Node.js is in scope. |
| D7 | Trivy 0.76 output | Recorded samples show rule IDs as `DS-0001` / `KSV-0001` (no `AVDID` key) and no `CauseMetadata.Resource`. The parser still reads `AVDID` and `Resource` when present, so older/newer versions work. Without a resource name, same-rule findings in one file collapse into one finding with `occurrences > 1`. |
| D8 | Gitleaks paths | Gitleaks reports paths as given on the command line. Paths are made relative to the scan root; an absolute path that is somehow outside the root is reduced to its file name. |
| D9 | Gitleaks stderr | `run_tool(..., keep_stderr=False)` sends Gitleaks stderr to `/dev/null`, so it is never held in memory at all. |
| D10 | Process isolation | Scanners run in their own session; on timeout the whole process group is killed (SIGKILL). |
| D11 | Unredacted test sample | The "unredacted Gitleaks report" used by leak tests is built in memory from `tests/fixture_secrets.txt` instead of being stored as another file, so fake secrets live in exactly one place outside the fixture. |
| D12 | Scanner working directory | Scanners run with `cwd` set to the private temp directory, not the target, so a scanned project cannot inject tool configuration (e.g. `trivy.yaml`) through the working directory. |
| D13 | Stored exception text | For unexpected adapter exceptions only the exception type name is stored (for every adapter, not just Gitleaks), because exception text could echo report content. |
| D14 | Summary counts | `summary.total` and `by_severity` count every stored finding, including false positives; `summary.false_positives` gives their number. Only the risk score excludes them. |
| D15 | Module layout | Read-model assembly helpers (`load_findings`, `build_summary`, `scan_detail`, `recompute_risk`, `comparison`) live in `db.py` and `ApiError` lives in `models.py`, keeping the `devguard/` module tree identical to §3 of the specification. |
| D16 | List responses | `GET /api/scans` returns `{"items": [...], "targets": [...]}` and findings lists return `{"total": n, "items": [...]}` so the UI can paginate and build target filters without extra endpoints. |
| D17 | Trivy stderr (known limitation) | As specified, the last 2000 characters of Trivy's stderr are stored in `scanner_runs.error_message` when Trivy fails. Trivy runs with `--quiet` and reports errors about its own operation (database download, parse failures), not file contents, but DevGuard does not inspect that text. Gitleaks stderr is never captured at all. |
| D18 | Comparison of the same scan | `GET /api/compare` with `base == head` returns `400 same_scan`. |
| D19 | Evaluation evidence export | Added `GET /api/evaluation/runs/{id}/export` (Markdown attachment) for the "Export evidence" button, so the file is produced server-side with the same escaping as scan exports. |
| D20 | Evaluation scans | The evaluation run performs three scans (vulnerable-app twice, then fixed-app); the repeat proves fingerprint stability. Check 03 inspects the database bytes, the API payloads as built by the same functions the routes use, and all three export formats for every scan. |
| D21 | Export of unfinished scans | Exporting a `queued` or `running` scan returns `409 scan_not_finished`. |
| D22 | HTML export CSP | The exported HTML file carries its own `<meta>` CSP (`default-src 'none'; style-src 'unsafe-inline'`), so it cannot load or run anything even when opened from disk. |
| D23 | Request-scoped SQLite connections | Each HTTP request opens its own connection with `check_same_thread=False`, because FastAPI may set up the dependency and run the endpoint on different worker threads. The connection is still used by one thread at a time. Scanner and evaluation threads keep the strict default. |
| D24 | Failed scans in the risk trend | §11 says partial scans are drawn as hollow points. Failed scans are incomplete too (their score of 0 only means no scanner produced results), so the trend chart draws every `partial` or `failed` scan hollow and labels it "(<status> scan, incomplete)". A failed scan at 0 never looks like a solid drop to a clean result. |
| D25 | `/docs` without a CDN | §10 keeps FastAPI's `/docs` open, while §2 forbids CDNs and external network resources. FastAPI's built-in page loads Swagger UI from `cdn.jsdelivr.net` with an inline script, which would run third-party code in the same origin as the API. `/docs` therefore serves a local page (`static/docs.html`, `static/js/docs-init.js`) using Swagger UI 5.34.1 vendored unmodified under `static/vendor/swagger-ui/` (Apache-2.0, licence included). Its CSP keeps `script-src 'self'` and only adds `'unsafe-inline'` to `style-src`, which Swagger UI needs. `/redoc` is disabled. |
| D26 | Host header and fetch-metadata checks | Besides the Origin check on state-changing requests, every request must carry a `Host` of `127.0.0.1` or `localhost` (with or without the configured port), else `403 host_not_allowed`; this blocks DNS rebinding. `/api/*` requests with `Sec-Fetch-Site: cross-site` get `403 origin_not_allowed`. |
| D27 | Triage and older scans | Per §8.2 a triage change re-scores only the latest scan of that target. Older scans keep the score they finished with, so the risk trend stays a record of what was known at the time; their finding lists still show the current triage status. |
| D28 | Fixture credential formats | GitHub push protection rejected the fake Slack bot token and AWS key pair in `vulnerable-app`. As §13 requires, the value formats were changed instead of bypassing the protection: the fixture now holds a generic API key, a fake signed session token (JWT), a database password and a fake GitHub PAT. Gitleaks still reports four findings (`generic-api-key` ×2, `jwt`, `github-pat`). The recorded sample in `tests/samples/` predates this and still shows the earlier rule IDs; it only feeds parser tests. |
| D29 | Windows support | The spec targets macOS; Windows 10/11 support was added on request. Scanners run in their own process group and are killed with `taskkill /T /F` on timeout (POSIX keeps `killpg`). Stored paths always use forward slashes, so fingerprints are identical across platforms. The private temp directory relies on the user-profile ACL instead of mode 0700. A GitHub Actions workflow runs the unit tests and the real-scanner evaluation on macOS and Windows. |
| D30 | Scanned projects cannot weaken the scan | Running scanners from a private temp directory keeps Trivy from reading a project's `trivy.yaml` / `.trivyignore`, but Gitleaks reads `.gitleaks.toml` from the scanned directory and honours `gitleaks:allow` comments. A project could therefore report zero secrets as a successful scan (invariant 2). Gitleaks now always runs with `--config devguard/adapters/gitleaks.toml` (built-in rules only), `--gitleaks-ignore-path` pointing at the empty report directory and `--ignore-gitleaks-allow`. Consequence: DevGuard never honours project-level Gitleaks allowlists; use triage (false positive) instead. |
| D31 | Triage re-scores the latest finished scan | "Latest scan" in §8.2 is read as the latest scan that has finished. A queued or running scan has no score yet, so it is skipped when a triage change is re-scored. |
